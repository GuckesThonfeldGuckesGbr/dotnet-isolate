# `list-files` verb, and moving the CLI to explicit verbs (FR-17)

## Problem

A CI pipeline building several services out of one solution wants to skip rebuilding a service
whose dependency closure didn't change since some base ref. `dotnet isolate` already computes the
exact answer to "which files does this `.csproj` depend on" — it's `Pipeline.isolate`'s `allFiles`,
after FR-15 artifact filtering — but the only way to get at it today is to actually materialize an
output folder and walk it, which is wasted I/O (hardlinking or copying) for a question that never
needed a folder in the first place.

## The new verb

`dotnet isolate list-files <path>... [-s <path>] [--restore]` runs project-graph resolution (step
1), file resolution (step 2), implicit repo-level file resolution and FR-15 artifact filtering
(step 3), then stops — no mirror root, no materialization, no solution-file generation. It prints
the resolved file set, one absolute path per line, to stdout; nothing else goes to stdout, so the
output is safe to pipe straight into `xargs`, `comm`, or a diff.

Included in the list, same as a real isolate run would place them:

- every file resolved from the entry projects' transitive `ProjectReference` closure (steps 1–2)
- implicit repo-level files up to the solution root (FR-10)
- **FR-16 foreign-project files** — reported as a warning (below), but still listed: they are real
  build inputs the closure consumes, exactly as `materialize` still copies them

Excluded, same as a real isolate run would drop them:

- **FR-15 build artifacts** (`bin/`, `obj/`, `node_modules/`, logs, declared output directories) —
  these are regenerated by the container's own build, so a host-side change to one is not a reason
  to skip a rebuild
- **FR-14 missing item files** — never existed on disk, so trivially not a dependency

`--restore` narrows the list to the same `Phase.restoreSubset` that `materialize --restore` writes,
for a pipeline with a separate restore-cache-skip check from its full-build one. `-s`/`--solution`
behaves exactly as it does for `materialize` — the ceiling for ancestor-globbed items.

`-o`/`--output-dir` and `--clean` are rejected: neither applies to a verb that writes nothing (see
"CLI shape" below for why they're still declared on the parser rather than simply omitted).

### Output channel discipline

stdout carries only the file list, one per line, sorted (ordinal string sort on the already
platform-normalized `Path.GetFullPath` output) for determinism across runs and platforms. Solution
discovery's "using solution: ..." line (FR-8) and every FR-14/15/16 warning move to stderr, the same
convention `materialize` already uses for its own warnings (`Report.warnings`). A script piping
`list-files` output into a diff must never have to filter out incidental text.

### Failure behavior

`Pipeline.listFiles` reuses the same hard failure as `Pipeline.isolate` when resolution produces no
files at all ("no build-relevant files were resolved for ...") — same message, same exit code path
through `Program.fs`'s existing `ArguParseException`/generic-exception handlers.

## CLI shape: full verbs, no back-compat

The tool moves from one implicit action to two explicit Argu subcommands. This is a breaking
change; there is no shim for the old verbless invocation, since the project isn't yet published to
nuget.org (per `AGENTS.md`: "feature-complete for a v0.1 release, not yet published").

    dotnet isolate materialize <path>... [-o <dir>] [-s <path>] [--restore] [--clean]
    dotnet isolate list-files  <path>... [-s <path>] [--restore]

`materialize` is today's behavior, renamed — DESIGN.md already calls the copy-into-output-folder
step "materialize" (step 6), so the verb matches vocabulary the codebase already uses. It keeps
every existing flag and behavior unchanged, including the multi-project `-o` requirement (FR-13):
with more than one entry project there is still no single default output folder name to fall back
to, and that requirement is specific to materialization, not to the tool as a whole.

`list-files` waives that requirement: with no output folder, there's nothing to disambiguate a
name for, so multiple entry projects are accepted without an `-o`.

Implemented as two Argu argument types under one top-level union:

```fsharp
type MaterializeArgs =
    | [<MainCommand; ExactlyOnce>] Project_Paths of paths: string list
    | [<AltCommandLine("-o")>] Output_Dir of dir: string
    | [<AltCommandLine("-s")>] Solution of path: string
    | Clean
    | Restore
    interface IArgParserTemplate with member this.Usage = ...

type ListFilesArgs =
    | [<MainCommand; ExactlyOnce>] Project_Paths of paths: string list
    | [<AltCommandLine("-s")>] Solution of path: string
    | Restore
    // Declared even though list-files never honours them (see below), so Argu recognizes and
    // consumes the tokens instead of falling through to Project_Paths.
    | [<AltCommandLine("-o")>] Output_Dir of dir: string
    | Clean
    interface IArgParserTemplate with member this.Usage = ...

type Arguments =
    | [<CliPrefix(CliPrefix.None)>] Materialize of ParseResults<MaterializeArgs>
    | [<CliPrefix(CliPrefix.None)>] List_Files of ParseResults<ListFilesArgs>
    interface IArgParserTemplate with member this.Usage = ...
```

**Why `Output_Dir`/`Clean` are declared on `ListFilesArgs` at all, instead of simply omitted:**
verified directly against the installed Argu 6.2.5 that `[<MainCommand>] Project_Paths of string
list` does not reject unknown flags — it silently folds them into the path list. (This is
pre-existing behavior of the *current*, single-type `Arguments`, not something the subcommand split
introduces: `dotnet isolate foo.csproj --bogus-flag` today parses to
`Project_Paths ["foo.csproj"; "--bogus-flag"]` with no error, confirmed with a throwaway probe
project against the real package.) Omitting the cases entirely, as originally spec'd, would mean
`dotnet isolate list-files foo.csproj -o bar` silently treats `"-o"` and `"bar"` as two more
(bogus, nonexistent) project paths and fails later with a confusing MSBuild "project not found"
error instead of a clear CLI message — worse than either flat-out accepting or rejecting the flag.

So the flag-conflict question is *not* answered by the type alone. `Program.fs`'s `main` parses the
top-level union, dispatches on `results.GetSubCommand()`, and the `List_Files` branch explicitly
checks `sub.Contains(Output_Dir) || sub.Contains(Clean)` and fails with a clear message
("`-o`/`--clean` are not valid with list-files; it never writes an output directory") before
building `ListFilesOptions` — a small, scoped runtime check on exactly the two flags that don't
apply, not a general validation pass.

## Pipeline refactor

`Pipeline.fs`'s `isolate` currently inlines steps 1–3 (project graph, file resolution, implicit
files) and FR-15/FR-16 filtering before continuing into mirror-root computation and materialization.
That prefix is exactly what `list-files` needs and nothing else, so it's extracted into a private
`resolve` function shared by both entry points:

```fsharp
type private Resolved =
    { Projects: string list
      SolutionRoot: SolutionDiscovery.SolutionRoot option
      Files: string list                                    // post FR-15 filtering
      ExcludedArtifacts: string list
      ForeignProjectFiles: ForeignFiles.ForeignGroup list
      MissingFiles: string list
      EntriesOutsideDiscoveredSolution: string list }

let private resolve (projectPaths: string list) (solutionPathOverride: string option) : Resolved =
    // steps 1–3 + FR-15 + FR-16, exactly the logic already in `isolate` up through
    // `artifactPartition.Kept`, unchanged in behavior — moved, not rewritten.
```

`isolate` calls `resolve`, then continues with everything from mirror-root computation onward
exactly as today (output-dir partitioning, `--clean`/materialize validation are specific to
writing an output folder, so they stay in `isolate` and are never seen by `list-files`).

`listFiles` is new:

```fsharp
type ListFilesOptions =
    { ProjectPaths: string list
      SolutionPath: string option
      RestoreOnly: bool }

type ListFilesResult =
    { Files: string list                                    // sorted, absolute
      Projects: string list
      SolutionRoot: SolutionDiscovery.SolutionRoot option
      ExcludedArtifacts: string list
      ForeignProjectFiles: ForeignFiles.ForeignGroup list
      MissingFiles: string list
      EntriesOutsideDiscoveredSolution: string list }

let listFiles (options: ListFilesOptions) : ListFilesResult =
    let projectPaths = options.ProjectPaths |> List.map Path.GetFullPath
    let resolved = resolve projectPaths options.SolutionPath
    let files =
        (if options.RestoreOnly then Phase.restoreSubset resolved.Projects resolved.Files else resolved.Files)
        |> List.sortWith String.CompareOrdinal
    if List.isEmpty files then
        failwith $"no build-relevant files were resolved for {String.concat ", " projectPaths}"
    { Files = files
      Projects = resolved.Projects
      SolutionRoot = resolved.SolutionRoot
      ExcludedArtifacts = resolved.ExcludedArtifacts
      ForeignProjectFiles = resolved.ForeignProjectFiles
      MissingFiles = resolved.MissingFiles
      EntriesOutsideDiscoveredSolution = resolved.EntriesOutsideDiscoveredSolution }
```

## New requirement: FR-17 (REQUIREMENTS.md)

> **FR-17** — `list-files` prints the same resolved file set `materialize` would place into an
> output directory — after FR-15 artifact filtering, including FR-16 foreign-project files — as one
> absolute path per line on stdout, without writing anything to disk. Intended for a CI step that
> compares the list against `git diff --name-only` to decide whether a service's dependencies
> actually changed, and skip an otherwise-identical rebuild when they didn't. `--restore` narrows
> the list to the FR-11 restore subset. Solution-source and FR-14/15/16 diagnostics go to stderr,
> never stdout, so the file list is safe to consume directly.

## README

The "Usage" section gets both verb forms. A new subsection after "How this keeps a Docker build
cached" shows the CI cache-skip recipe, since paths are printed absolute and `git diff` reports
repo-relative paths — the worked example needs to show the relativization:

    ## Skipping a rebuild when nothing changed

    `list-files` prints a service's exact dependency set, so a CI step can skip an unchanged
    service's build/test stage entirely instead of relying on coarse path filters.

        repo_root=$(git rev-parse --show-toplevel)
        deps=$(dotnet isolate list-files src/Service1/Service1.csproj | sed "s|^$repo_root/||" | sort)
        changed=$(git diff --name-only "$BASE_SHA" HEAD | sort)

        if comm -12 <(printf '%s\n' "$deps") <(printf '%s\n' "$changed") | grep -q .; then
          echo "dependencies changed — build required"
        else
          echo "no dependency changes — skipping build"
        fi

    `BASE_SHA` is whatever your CI provider exposes for "the commit this branch diverged from" —
    e.g. the merge-base with the target branch for a pull request.
